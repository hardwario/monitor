## User experience

### Console bottom bars (#5, ADR-0378)

The command input (console pane), the shell search bar and the log search bar (log pane) all have the height
`Theme.toolbarHeight` (40 = `controlHeight` 32 + 2×`spacingXs`). Fields and buttons are `controlHeight` (32) high
(segments and level chips are centred, may stay smaller). Side by side, the separators and the controls line up.

### Log toolbar (#6, ADR-0379)

One row, never wraps: `[Search|Filter] [field ………………… (Showing 12 of 340)] [D I W E H] [✕]`.

- The search field fills the remaining width (minimum 120 px).
- **✕** is a small icon button right of the level chips (tooltip "Clear filter", accessible name "Clear filter"),
  visible only when the filter differs from the default (`filterActive`); its space is not reserved.
- Filter mode: "Showing %1 of %2 lines" becomes a muted suffix inside the field, elided; the full text as tooltip.
- The wide "✕ Filter: levels" / "Filter: %1" chip and the "Clear filter" button are removed. In Search mode a
  text filter set earlier is shown by the ✕ and the field's suffix "Filter: %1" (elided, tooltip full).
- Bar height is the same with and without the filter at 960×600, 1099×700 and 1280×800 in Czech.

### Cable illustrations (#7, ADR-0380)

New schematic SVGs (line drawings, no text): CHESTER board outline with the two 10-pin programming connectors (APP
and LTE) at their real positions, the J-Link flat cable on the connector of the step, that connector highlighted in
the accent colour, the other one muted. `chester-app-cable.svg`, `chester-lte-cable.svg` and `-dark` variants,
480×270. The drawing must be checked against a real CHESTER board (connector positions) before merge.

### Application copy after a cancelled LTE update (#8, ADR-0381)

- **Cancel after the erase**: the Cancel confirmation (ADR-0067) asks "The application MCU is erased. Write the
  application back first?" — **Write back** (moves to "Connect the J-Link to APP" → writes the copy → done, wizard
  says "LTE firmware not updated. The application was written back.") · **Leave it erased** (cancelled, as today:
  "The copy of the application stays in %1") · **Back**. Without a copy (empty application) the old text stays.
  A remote-started update keeps ADR-0368 (support decides; the copy is always written back).
- **Flash page and step 7**: the application `SourceCard` shows, when copies exist for the connected device's
  serial, a row "Application copy from %1" (local date/time) for the newest copy; a menu lists up to 10 copies of
  that serial. Choosing it loads the hex like a file.
- **Open backups folder**: a button in that row (and in the Cancel result toast); the step 7 / Flash file dialogs
  start in the backups folder when the kind is application and copies exist.

### Error panels in a wizard (#9, ADR-0382)

Inside a wizard an `ErrorPanel` shows no Dismiss / primary action and no "Help me fix this" (the footer has Try
again / Cancel). Instead it shows a link "Troubleshooting" to the documentation's troubleshooting section for that
error code (the existing docs link helper from plan 0037). Applies to every `ErrorPanel` inside `WizardDialog`,
including the embedded `SourceCard`s.

### LTE update failures in the guided flow (#9, ADR-0383)

- The guided flow (GUI wizard, `--guided`, remote) does not rewrite a failure into `target.reset_during_update`; the
  reset reason is only logged (the application is erased there, it cannot be the cause).
- nRF Util output containing `LOW_VOLTAGE` (e.g. "Failed to configure Coresight: LOW_VOLTAGE") becomes the new
  `target.low_voltage`: "The LTE MCU reports too low supply voltage." · why: "The CHESTER is not powered enough
  (battery, power supply) or the J-Link cable does not connect the supply reference." · what to do: "Check the power
  supply or batteries of the CHESTER and the J-Link cable on the connector, then try again." Category target.
- In the guided flow the suggestion of `firmware.modem_update_failed` and `target.low_voltage` is the guided variant:
  "Check the power supply of the CHESTER and the J-Link cable on the LTE connector, then click Try again." It never
  says "use the guided update". The plain flow keeps the existing texts.

### Wizard scroll hints (#10, ADR-0384)

- `WizardDialog` content: vertical scroll bar `AlwaysOn` while the content is taller than the view (hidden otherwise).
- A fade (gradient from transparent to the dialog background, 24 px) at the bottom edge while more content is below.
- Step 7: choosing "Firmware from the catalog or a file" scrolls the expanded picker into view (animated, top of the
  picker at the top of the view, as far as possible).

### Recent entries by name (#11, ADR-0385)

- A catalog entry shows "hio-chester-meteo v4.0.1" as its name; the type column keeps "Catalog ID"; the tooltip is
  "Catalog ID 59489e4e…" (full ID). A file entry keeps its file name, tooltip the full path (unchanged).
- Entries are stored with `name` and `version` when added (from the catalog lookup).
- Entries stored before (no name) are looked up in the background when the Recent list is shown: one at a time, at
  most 10, each ID at most once per run; a found name is written into the stored entry; while unknown or when the
  lookup fails, "Catalog ID %1" stays.

## CLI

- `hwio chester app backups [--serial N] [--json]`: lists the application copies (newest first: time, serial, path,
  size). Without `--serial` the connected device's serial (if a probe is connected), else all.
- `hwio chester app flash --backup latest|PATH`: flashes the newest copy of the connected device's serial (or the
  given file from the backups folder); refuses when the copy's serial differs from the device (`--force` overrides).
  Exit codes as `app flash`.
- `hwio chester lte flash --guided`: Ctrl+C / "n" after the erase asks "Write the application back first? [Y/n]"
  (no terminal: writes back). Guided texts per ADR-0383.

## Implementation notes

Small choices made while implementing (not architectural; listed for the review). The points marked **(confirmed)**
were confirmed by the user on 2026-11-17 (with #8 serial and the CLI wording of #9 guided flag).

- **#6** At 1099×700 side by side in Czech the widest row (Search mode with a match count, ↑ ↓ ×, an active filter ✕)
  did not fit; the search's match count "3 / 128" is therefore also a muted suffix inside the field (like the filter
  count). An invalid regular expression is an elided suffix inside the field too ("searchError", tooltip full text).
  The test checks this widest row as well.
- **#7** The connector positions of the schematic drawing (APP left, LTE right of the board) are not verified; the
  SVG `<desc>` and the folder README say so (Risks).
- **#8 procedure** The copy is kept separately from the image chosen in step 7, so Write back after a cancel always
  writes the copy. `Options::restoreOnCancel` (new; true for a remote-started update in the GUI and in `remote host`)
  writes back without OfferRestore; `autoRestore` keeps its meaning (step 7 without waiting, the CLI). A second
  cancel on the way back ends erased. After a write-back the procedure ends as `Cancelled` with `writtenBack()`; the
  text says "LTE firmware not updated. The application was written back." or, when the LTE MCU had already been
  updated, "The LTE firmware was updated. The application was written back." The remote reporter now takes "LTE MCU
  updated" from the procedure (`lteUpdated()`), not from reaching the APP connector again (which the write-back also
  does); a written-back remote update reports `cancelled`.
- **#8 wizard** The Cancel confirmation's third button is a small, optional extension of the wizard framework
  (`Wizard::cancelAlternativeText/cancelAlternative`, `ConfirmDialog.alternativeText`): accept = **Leave it erased**
  (red), alternative = **Write back** (primary), reject = **Back**. A closed tab or the tab's busy callback leaves the
  application erased (as before). After Write back the wizard stays open and ends on a Done step "LTE firmware update
  cancelled" with the procedure's text. A remote-started update asks the old two-button question with the text
  "Cancelling writes the application back first …".
- **#8 toast (confirmed)** Toasts have no buttons, so the Cancel result toast says only "The copy of the application
  stays in %1."; **Open backups folder** is on the application card (Flash page, step 7).
- **#8 serial** The Flash page takes the device's serial from `info show` (the last known one is kept while the
  application is erased); the wizard from the PIB read before the copy. While no serial is known the card lists all
  copies as "Application copy of %1 from %2".
- **#8 CLI** `app backups` without `--serial` reads the PIB of the connected device (all copies when that fails);
  `app flash --backup PATH` also accepts a file name of the backups folder; `--backup` with a HEX file/ID is a usage
  error. Ctrl+C is applied once (the stop request stays set; a second `cancel()` would end the offered write-back).
  `askYesNo` got a default-yes variant for "[Y/n]".
- **#9 ErrorPanel (confirmed)** Inside a wizard the existing "Learn more ↗" link (plan 0037, same URL) reads
  **Troubleshooting ↗** instead of adding a second link. The SourceCard panels keep their primary action inside a
  wizard (`keepPrimaryInWizard`): the designated firmware's **Retry** and **Choose another file** work there and are
  the only way to retry a failed download in step 1; ADR-0382 says to hide the primary action of every panel —
  hiding these would strand that state. `inWizard` is found by walking up to `WizardDialog`'s `wizardContent`.
- **#9 guided flag** `FlashOptions::guided` (and `updateModem(..., FlashOptions)`, where only `guided` applies)
  carries the flag to the worker; the procedure sets it for the LTE update and the restore. The guided suggestion is
  applied by `withGuidedLteSuggestion()` (libs/core) in `LteUpdateProcedure::fail()`. In the terminal (`--guided`)
  "click Try again" does not fit: the CLI says "…, then run the command again."
- **#10** The fade and the scroll animation are siblings of the `ScrollView` in a wrapping `contentItem`; an embedded
  step asks for scrolling with a `scrollIntoViewRequested(item)` signal (connected with `ignoreUnknownSignals`). Step 7
  scrolls 50 ms after the choice (once the picker is laid out).
- **#11** The tooltip of a catalog entry (DetailRole) is "Catalog ID <id>" also before the name is known. The lookup
  is triggered when the Recent list becomes visible (`resolveRecentNames()`); "each ID once per run" is per firmware
  source view model (one per Flash page and wizard), bounded by 10 lookups each.
- **Tests** The step-7 Qt Quick test runs the guide on a two-connector fake board (`testSupport.writeText()` for the
  connector file); the CLI e2e test sends SIGTERM (handled like Ctrl+C) and is POSIX only.
- **Release notes** `packaging/release-notes/v2.0.0-rc.5.md` was started with these fixes.
